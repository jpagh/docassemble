## Objective and implementation

`Preparation.prepare` accepts `operation='update'` with a normalized distribution
name, or `operation='remove'` with a name and an explicit `contribution_id`.
Neither operation accepts changed constraints/extras/markers/ownership. Update
keeps every original contribution. Removal deactivates only the selected active
interactive contribution of the owned identity; configuration contributions,
unrelated identities and other interactive contributions remain enforced.

The independent pinned-uv builder verifies the complete retained parent bundle
and seeds `uv.lock` from its original `solve.lock`. Update invokes
`uv lock --no-config --upgrade-package <normalized-name>`; Removal invokes the
same lock command without an upgrade flag. These are preferences, not hard pins:
necessary non-core movements remain possible, while unrelated selections are
preferred. There is no update-all. Complete desired-relative and verified-runtime-
relative diffs cover **all** solver movements. Exact core versions/source hashes,
durable materialization and cold-cache frozen/no-build validation remain required.

Both operations use the existing immutable readiness digest, five-minute expiry,
fresh approval checks, atomic publication, single installation slot, durable
polling, maintenance/drain, non-root frozen application and terminal reporting.
No legacy uninstall, discovery/repair loop, separate dispatcher or new schema.
Existing preview transports accept the operation/contribution fields; no general
API or new configuration/browser operation-picker UI is claimed.

Update permission is distinct from contribution/source-edit permission. The SQL
authorizer permits an authorized non-owner to update without editing declarations
or transferring ownership; the public qualified bridge retains its existing
administrator-only restriction. Removal remains owner-authorized. Publication
compares the projected owner to the previewed current owner, rather than assuming
that updater and owner are identical. Package/identity rows and current grants
survive final removal and same-owner reactivation. Package.active projects
remaining **interactive** intent, not transitive/config-installed inventory.

The lifecycle fixture's build-only wrapper now seeds its disposable baseline
before `populate_tables`, whose accepted account/default-role writers correctly
require the singleton. Production create_tables is unchanged; a new PostgreSQL
regression proves absent-singleton rejection in production on both schema paths.
This fixture-only adjustment was explicitly approved by the supervisor. The
05b2b9 handoff now says “distinct invitation tokens generated by the test signer”.
